## 为什么做差了

1. **把 Demo 当成生产平台重建。** 本来只需“输入 -> Skill 规划 -> 故事板确认 -> Provider -> 资产预览”，实际加入 V5 迁移、durable outbox、候选版本、复杂审批、训练表、备份、洞察和多轮安全审查。
2. **没有先做 Skill 路由。** 已有 storyboard、continuity、production board、Seedance reference、API interface、QC 等本地 Skill，足够做薄编排层。本轮没有先逐项读取并组合，也没有完成用户要求的社区/开发者经验联网研究。
3. **前端时间严重不足。** 后端和迁移占绝大多数，集中前端实现只有约 10 分钟；没有先锁高保真原型、关键交互和视觉验收，所以页面信息密度、确认感和素材表现不够专业。
4. **把测试覆盖误当成产品完成。** 129 tests、build 和 secret scan 是工程证据，不是客户价值。最新版本没部署，测试再多也不能算交付。
5. **错误设置关键路径。** 16 秒双镜真实生成应该是后台证据，不应阻塞公网发布；Playwright 也不应等待 Provider 十多分钟。
6. **Agent 输出没有收束成单一里程碑。** Inspector 隔离正确、监控只读，但主 Agent 同时推进开发、迁移、真实生成、文档和部署，导致三个冻结点和三份审查报告并存。
7. **没有在 30 分钟处做产品可见性检查。** 若当时强制打开页面并问“剪辑师是否能立刻理解和确认”，会更早发现投入方向错误。

## 本可采用的 120 分钟 MVP 路径

| 预算 | 唯一产物 | Gate |
| ---: | --- | --- |
| 15m | 读取已有 Skill/API 能力，形成 1 页调用矩阵 | 不自研已有能力 |
| 20m | 一个高保真工作台原型 | 用户能看懂输入、确认、进度和资产 |
| 30m | FastAPI 薄编排与服务端密钥/额度 | 无码 401、两队列、真实状态 |
| 30m | React 三栏页面与故事板确认 | 桌面/移动无错位 |
| 15m | fake E2E、1 图和 1 条 4s 视频 smoke | 不等待长视频 |
| 10m | 原子部署、healthz、回滚点 | 先给网址，再扩验收 |

长视频、多镜拼接、历史迁移、A/B、周报和训练飞轮应在新 MVP 可用之后并行建设，而不是压在首次交付前。

## 新的执行纪律

- 只有主 Agent 修改代码；Inspector 只审最终冻结提交；不再配置持续监控 Agent。
- 每 30 分钟必须产生一个可打开、可点击、可部署的用户结果。
- 真实 Provider 任务与部署解耦；单项等待超过 15 分钟立即结束测试等待，但不取消服务端任务。
- 先 Skill/API 复用矩阵，后写代码；先 UI 原型 Gate，后扩数据合同。
- 发布版本、Git HEAD、Inspector 冻结点必须相同，否则不得报告“已交付”。
